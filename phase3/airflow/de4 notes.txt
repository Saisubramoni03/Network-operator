REQUIRED EXPLICIT JUSTIFICATIONS

1. Batch, because streaming would add cost without adding value here

Hotspot alerts are the clearest example.

The source data itself only updates once per hour. Building a Kafka streaming
pipeline to detect hotspots in real time would mean reacting to data that is,
at best, an hour old anyway.

Streaming infrastructure such as Kafka brokers, stream processors, and
always-on compute would add operational cost and complexity. However, the
alert cannot become more current than its hourly source data.

Therefore, a batch or micro-batch process that runs once per hour, shortly
after the file arrives, provides the same effective freshness with much less
cost and complexity.


2. Hypothetical streaming justification

If the system evolves to ingest true per-event network signaling data instead
of the current hourly aggregates, streaming would provide clear business
value.

For example, a cell tower failure or sudden traffic spike may need to be
detected within seconds. Waiting for an hourly batch process could delay the
response and increase customer impact.

In that situation, the business requirement for rapid incident detection
would require lower latency than the current data source can provide. This
would be a strong reason to introduce Kafka and a streaming architecture.


WHERE KAFKA COULD CONCEPTUALLY ENTER

Kafka would sit between the raw event source and the rest of the architecture
as a new ingestion layer:

[Cell Towers Emit Raw Events]
            |
            v
[Kafka Topic: raw_activity_events]
            |
            v
[Stream Processor]
(Near-Real-Time Micro-Aggregation)
            |
            v
[Kafka-Backed Store / Data Store]
            |
            v
[Existing Batch Pipeline]
(Spark / Warehouse / Dashboards)


The current CSV files would essentially be replaced by Kafka-backed event
ingestion if this became a live production system.

The existing downstream batch components, such as Spark processing,
warehouse storage, and dashboards, would not necessarily need to change.
The main change would be replacing the static CSV ingestion layer with a
real-time event ingestion layer.


REVISED ARCHITECTURE NOTE

The streaming path is optional and conceptual only. It is not implemented
in the current project.

Nothing in Phase 2 or Phase 3 needs to change to support this future
extension. Kafka is presented only as a possible future ingestion layer if
the business later requires true real-time network event processing.
